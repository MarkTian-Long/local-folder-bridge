# 现有插件的配置处理

适用：原网页插件“本地文件（只读）”，以及本机文件桥 1.1.x。本文没有宣称已经替用户修改账号配置。

## 先分清三个部分

本机文件服务是本包；隧道进程是官方 `tunnel-client`；ChatGPT 插件是云端的工具入口。原本机程序丢失后，需要恢复本机服务与隧道运行条件，但不必先删除云端插件。App ID、Version ID 与 Tunnel ID 分别标识不同对象，不可互填。

旧版返回过 404，说明那次请求链路失败，不能仅据此推断是授权目录不足、服务没启动、隧道已删除中的哪一种原因。本包默认不扩大目录范围解决连接错误。

## 复用或重建的判定

| 核验结果 | 对网页配置的动作 |
|---|---|
| 原 Tunnel 存在且可运行，原插件仍绑定它 | 本机填旧 Tunnel ID，启动健康后刷新工具；无需删除原插件 |
| 原 Tunnel 存在但权限/工作区关联错误 | 先按平台权限修正关联；本机代码不代替账号授权 |
| 原 Tunnel 已失效或无法恢复 | 创建有效新 Tunnel，本机与网页都绑定它；编辑入口不支持更换时新建连接 |
| 工具还是原来的 3 个定义 | 服务启动后刷新，再开新对话启用；不可把缓存发现当成新代码已上线 |
| 需要文件操作 | 本机开启全局和指定目录权限，再刷新工具；ChatGPT 仍须按其平台策略确认 |

OpenAI 官方现行步骤：在插件页新建开发者连接，Connection 选择 Tunnel，选择或粘贴有效 ID；创建者需要 Tunnels Read + Use，Tunnel 要关联目标工作区。创建/编辑 Tunnel 另需 Read + Manage。来源：<https://developers.openai.com/api/docs/guides/secure-mcp-tunnels>。

## 刷新后应该发现的工具

只读默认 5 个：`get_status`、`list_files`、`search_files`、`read_file`、`get_operation`。开启操作总开关后再增加 4 个：`propose_write_file`、`propose_move_file`、`propose_create_directory`、`propose_trash_file`。即便平台缓存了操作工具，只要本机开关关闭，服务仍拒绝调用。

每个工具均有 `inputSchema`、`outputSchema` 和 annotations；输入拒绝未声明参数。只读工具声明 `readOnlyHint=true`、`destructiveHint=false`、`openWorldHint=false`。提案工具按可能造成文件变更声明非只读；写入、移动、回收标记破坏性潜力。最终标签由平台渲染，不能保证逐字对应截图的中文标签。

截图中的 `public` 是工具可见性信息，不能独立推出硬盘已经公开。相反，仅写着“只读”也不能证明后台确实只读。本包以目录校验、接口分离、开关和本机审批落实施工边界，而不是靠标签授权。

刷新工具定义的官方说明：<https://developers.openai.com/plugins/deploy/connect-chatgpt>。

## 权限不必一律改成“全部允许”

先保留原先的“允许低风险操作”默认设置。模型提出写入时即使网页批准，本机仍只建立 pending 提案；用户在本机界面核对并批准后才执行。远程无法调用本机的添加目录、审批或恢复管理接口。

本机服务分别监听两个 localhost 端口，使用不同随机凭证。Tunnel profile 通过环境变量向本机 MCP 请求附加 Authorization；无需把自动生成的本机凭证塞进截图所示的网页 OAuth 设置。本项目未实现公共 OAuth 服务，也没有把 MCP endpoint 开成公网服务。

## 必须完成的连接验收

先本机自检，再官方 doctor 与就绪，最后随机验证文件。最后一步只把读取路径提示给 ChatGPT，不把随机字符串告诉它；核对返回原文和本机调用记录。真正成功以前，不把“可发现工具”“进程在运行”“诊断通过”写成“已读取用户电脑”。
